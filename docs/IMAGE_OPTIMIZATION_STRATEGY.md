# Image Optimization Strategy

This document describes how images are optimized across the `rockypointnet-client` app. The app is an Astro site with embedded Qwik islands, which means two distinct image pipelines coexist. Each pipeline has different capabilities and constraints, so we split responsibility along the framework boundary.

## TL;DR

| Framework                                                             | Owner of optimization | Mechanism                                                                                                                                                        |
| --------------------------------------------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Astro (server-rendered pages, layouts, static assets in `src/assets`) | Astro                 | Built-in image service (`astro:assets` → `<Image />`, `<Picture />`)                                                                                             |
| Qwik (interactive islands)                                            | Us                    | [`qwik-image`](https://github.com/QwikDev/qwik-image) component + self-hosted [`imgproxy`](https://hub.docker.com/r/darthsim/imgproxy/) as the image transformer |

Astro images stay Astro's concern — its optimizer is already wired into the build and we don't touch it. The Qwik portion of the app does **not** ship a remote image optimizer out of the box, so we provide one ourselves via `imgproxy` running on our own infrastructure. This avoids per-transform fees from CDN image services (Cloudinary, Builder.io, Vercel Image Optimization, etc.) and keeps compute on hardware we already pay for.

## Boundaries

### Astro pipeline

- Used by `.astro` pages and components.
- Source assets live in `src/assets/` and are referenced through `astro:assets`.
- Astro emits multiple format/size variants at build time and serves them from `/`_`astro-generated paths`_.
- We do not change this. New images consumed only from `.astro` files should keep using `astro:assets`.

### Qwik pipeline

- Used by any `.tsx` file under `src/components/qwik/` (Qwik islands).
- Qwik core only provides a build-time `?jsx` import that emits a static `<picture>` with `srcset`. It cannot transform remote/runtime image URLs.
- For remote images, dynamically-sourced content (e.g., CMS, S3, user uploads), or any island that needs runtime resizing, we use the `qwik-image` component pointed at our self-hosted `imgproxy`.

## Architecture

```
                        ┌─────────────────────────────┐
                        │   Origin storage            │
                        │   (S3/Linode bucket, CMS, public)  │
                        └──────────────┬──────────────┘
                                       │  (HTTPS signed URL)
                                       ▼
┌──────────────────────────────────────────────────────────────────────┐
│  imgproxy  (Docker container, self-hosted on our infrastructure)     │
│  - Resizes, crops, format conversion (webp/avif), quality control    │
│  - Optional URL signing                                              │
│  - Built-in LRU + on-disk cache; sits behind a reverse-proxy cache   │
└──────────────┬───────────────────────────────────────────────────────┘
               │  https://img.<our-domain>/<signed-path>
               ▼
┌──────────────────────────────────────────────────────────────────────┐
│  Qwik island in the browser                                          │
│  <Image src="..." width=... height=... layout="constrained" />       │
│  generated by qwik-image using imageTransformer$ → imgproxy URL      │
└──────────────────────────────────────────────────────────────────────┘
```

## Why imgproxy

- **Single static binary** packaged as a Docker container — trivial to deploy alongside our existing services.
- **No per-image fee** — capacity is bounded by our own CPU/disk, not by a SaaS quota.
- **Hot path is fast** — written in Go with libvips; can saturate a CPU core on transforms.
- **URL signing** is built in, preventing third parties from using our optimizer as a free transform service.
- **Stateless** — the container itself caches in memory; durable caching is handled by an HTTP cache in front (Caddy / Cloudfront / Cloudflare).

Alternatives considered:

- **Cloudinary / Imgix / Builder.io** — Highest DX, but recurring per-image cost.
- **Vercel/Netlify image optimization** — Requires deploying to those platforms; ties us in.
- **Sharp at the edge / per-request in our Node server** — More code to maintain, no built-in signing, no built-in cache.

## Setup

### 1. imgproxy container

Provision an `imgproxy` instance reachable from the public internet (or from the CDN that fronts it). Example `docker-compose.yml` fragment:

```yaml
services:
  imgproxy:
    image: darthsim/imgproxy:latest
    restart: unless-stopped
    environment:
      IMGPROXY_BIND: "0.0.0.0:8080"
      IMGPROXY_USE_ETAG: "true"
      IMGPROXY_ENABLE_WEBP_DETECTION: "true"
      IMGPROXY_ENABLE_AVIF_DETECTION: "true"
      IMGPROXY_AUTO_WEBP: "true"
      IMGPROXY_AUTO_AVIF: "true"
      IMGPROXY_MAX_SRC_RESOLUTION: "50"
      IMGPROXY_QUALITY: "80"
      IMGPROXY_KEY: "${IMGPROXY_KEY}" # hex
      IMGPROXY_SALT: "${IMGPROXY_SALT}" # hex
      IMGPROXY_ALLOWED_SOURCES: "https://${ASSET_HOST}/"
    ports:
      - "8080:8080"
```

Notes:

- `IMGPROXY_KEY` / `IMGPROXY_SALT` enable URL signing. Generate with `xxd -g 2 -l 64 -p /dev/random | tr -d '\n'`.
- `IMGPROXY_ALLOWED_SOURCES` whitelists which upstream hosts can be transformed — keep this tight.
- Front the container with the same reverse proxy / CDN edge cache used by the rest of the app. The transform result is highly cacheable (immutable per URL).

### 2. `qwik-image` provider

Install the package:

```sh
bun add qwik-image
```

Register the provider once near the root of any Qwik island that needs optimized images. The provider hooks into Qwik's `useImageProvider` and tells `<Image>` how to construct an optimized URL.

```tsx
import { $, component$ } from "@qwik.dev/core";
import {
  Image,
  type ImageTransformerProps,
  useImageProvider,
} from "qwik-image";

const IMGPROXY_BASE = import.meta.env.PUBLIC_IMGPROXY_BASE;

export const SomeIsland = component$(() => {
  const imageTransformer$ = $(
    ({ src, width, height }: ImageTransformerProps): string => {
      // Encode the upstream URL and apply imgproxy processing options.
      // Format: /<signature>/<processing_options>/<encoded_url>.<ext>
      // For unsigned dev: use "insecure" signature.
      const encoded = btoa(src)
        .replace(/=/g, "")
        .replace(/\+/g, "-")
        .replace(/\//g, "_");
      return `${IMGPROXY_BASE}/insecure/rs:fill:${width}:${height}/${encoded}`;
    },
  );

  useImageProvider({
    resolutions: [640, 960, 1280, 1920],
    imageTransformer$,
  });

  return (
    <Image
      layout="constrained"
      objectFit="cover"
      width={1280}
      height={400}
      alt="Hero shot of Rocky Point"
      placeholder="#e6e6e6"
      src="https://assets.example.com/hero/sunset.jpg"
    />
  );
});
```

In production, replace the `insecure` segment with a properly signed path derived from `IMGPROXY_KEY` / `IMGPROXY_SALT`. The signing is HMAC-SHA256 over `/<processing_options>/<encoded_url>` — see [imgproxy's signing docs](https://docs.imgproxy.net/usage/signing_url).

### 3. Environment variables

- `PUBLIC_IMGPROXY_BASE` — base URL of the imgproxy edge (e.g., `https://img.rockypoint.net`). Must be `PUBLIC_*` since the Qwik island runs in the browser.
- `IMGPROXY_KEY`, `IMGPROXY_SALT`, `IMGPROXY_SIGN_KEY_VERSION` — server-side only; used by whatever service generates signed URLs (do **not** expose to the client).

## When to use which

- **Static asset in an `.astro` page** → Astro's `<Image />` from `astro:assets`.
- **Static asset in a Qwik island** → `?jsx` import for build-time optimization (no runtime image service needed).
- **Remote/dynamic image in a Qwik island** → `qwik-image` `<Image>` with the imgproxy transformer.
- **User-uploaded content** → Always through imgproxy (signed URLs); never `?jsx` (paths aren't known at build time).

## Caching strategy

Each cache layer answers a different question:

1. **Browser cache** — `Cache-Control: public, max-age=31536000, immutable` set by imgproxy. Transform URLs are content-addressable (the path encodes processing options + source), so they can be cached forever.
2. **CDN / reverse-proxy cache** — Fronts the imgproxy container; absorbs identical requests across users.
3. **imgproxy in-process cache** — Bounded LRU for hot transforms; minor optimization for cold-edge requests.
4. **Origin** — Untouched. imgproxy fetches the source on cache miss.

Cache key is the full path (processing options + encoded source). Invalidation = change the source URL (e.g., versioned object keys).

## Operational notes

- **Resource sizing**: budget ~1 CPU core and ~256 MiB RAM per concurrent libvips operation. Most transforms complete in <100 ms.
- **Disk**: imgproxy itself doesn't persist transforms — the CDN/edge cache does. The container can run on ephemeral storage.
- **Failure mode**: if imgproxy is unreachable, `<Image>` will render a broken image. Consider adding a health check + a fallback to a generic CDN URL or the unoptimized source.
- **Monitoring**: imgproxy exposes Prometheus metrics on `/metrics`. Useful counters: `imgproxy_requests_total`, `imgproxy_request_duration_seconds`.
